# Plan 10 — CI Reliability + FOUND-10 Docs Reconciliation

**Gap source:** 01-REVIEWS.md (Codex HIGH-3, MEDIUM-1, MEDIUM-3; LOW-1)

**Goal:** Make CI trustworthy on first push (golangci-lint compatible with Go 1.25), make the testcontainer isolation suite fail visibly when Docker is unavailable in CI, and align the FOUND-10 requirement text with D-25 reality.

## Context

- **Codex HIGH-3:** `golangci/golangci-lint-action@v6` at `.github/workflows/ci.yml:42` is pinned to `version: v1.63`. That binary was built with Go 1.23. The module declares `go 1.25.0` and `toolchain go1.25.10` in `services/api/go.mod:3-5`. Golangci-lint will refuse to analyse a module targeting a newer Go than the binary was compiled with. First PR CI will fail the `go-lint` job.
- **Codex MEDIUM-1:** `services/api/test/isolation/main_test.go:84-91` exits 0 when testcontainer bring-up fails. In a CI environment where Docker is unexpectedly absent, the entire isolation suite silently passes without running — providing a false green on the FOUND-08 gate.
- **Codex MEDIUM-3:** `REQUIREMENTS.md:30` FOUND-10 still says "the Go API, and the Vite dev servers" are brought up by `docker compose up`. Decision D-25 explicitly removed the API service and Vite dev servers from compose (devs run the API natively via `task dev`/air; Vite dev is Phase 2). The requirement text must match the implemented behaviour.
- **LOW:** `.github/workflows/ci.yml:137` `run:` step uses a YAML double-quoted scalar — switch to block scalar `|` for idiomatic multi-command steps.

## Task 2 — Fail-closed testcontainer setup when CI=true

<task name="testcontainer-fail-closed-ci" type="auto">
<read_first>
- services/api/test/isolation/main_test.go (all os.Exit(0) calls in TestMain setup)
</read_first>

<action>
In `services/api/test/isolation/main_test.go`, introduce a helper that chooses the exit code based on the `CI` environment variable. When `CI=true` (GitHub Actions sets this automatically), setup failures must exit 1 so the job is red-flagged. Outside CI, keep exit 0 so local devs without Docker can skip the suite.

**Add a package-level helper at the top of the file (after the `var` block):**

```go
// ciExitCode returns 1 when the CI env var is non-empty (GitHub Actions always
// sets CI=true). Used by TestMain to distinguish "Docker unavailable locally
// — skip gracefully" from "Docker unavailable in CI — fail loudly".
func ciExitCode() int {
    if os.Getenv("CI") != "" {
        return 1
    }
    return 0
}
```

**Replace every `os.Exit(0)` inside TestMain that follows an error write** with `os.Exit(ciExitCode())`. There are seven such call sites (postgres.Run failure, ConnectionString failure, sql.Open failure, pgmigrate driver failure, migrate.NewWithDatabaseInstance failure, migrate.Up failure, pgxpool.New failure). The normal `os.Exit(code)` at the end of TestMain (after `m.Run()`) stays unchanged — that's the test result exit, not a setup failure.

Specifically, replace:
- Line ~89: `os.Exit(0)` after `postgres.Run` failure
- Line ~98: `os.Exit(0)` after `pgC.ConnectionString` failure
- Line ~106: `os.Exit(0)` after `sql.Open` failure
- Line ~113: `os.Exit(0)` after `pgmigrate.WithInstance` failure
- Line ~124: `os.Exit(0)` after `migrate.NewWithDatabaseInstance` failure
- Line ~131: `os.Exit(0)` after `migrate.Up` failure (non-ErrNoChange)
- Line ~139: `os.Exit(0)` after `pgxpool.New` failure

Each replacement: `os.Exit(ciExitCode())`

The `os.Exit(code)` at line ~185 (after `m.Run()`) must NOT be changed — that's the test exit code.
</action>

<verify>
- `grep -c "os.Exit(ciExitCode())" services/api/test/isolation/main_test.go` returns 7 (one per setup failure site)
- `grep "os.Exit(0)" services/api/test/isolation/main_test.go` returns only 0 matches (no plain os.Exit(0) left in error paths)
- `go build ./test/isolation/...` exits 0
</verify>

<acceptance_criteria>
- `grep "ciExitCode" services/api/test/isolation/main_test.go` shows the helper function definition
- `grep -c "os.Exit(ciExitCode())" services/api/test/isolation/main_test.go` is at least 5

</read_first>

<action>
In the `compose-config` job's "Taskfile parses" step, change the `run:` value from a double-quoted YAML flow scalar to a block scalar (`|`). This is the idiomatic GitHub Actions form for shell commands and avoids any YAML-parser edge cases with `>` inside a quoted scalar.

```yaml

        run: "$(go env GOPATH)/bin/task --list > /dev/null"
```

**After:**
