## User Constraints (from CONTEXT.md)

### Locked Decisions

**Code Field Semantics (Area 1)**
- **D04_1-01:** `code` is a universal user-facing canonical identifier. Required (`TEXT NOT NULL`) on every primary catalog entity. Composite `UNIQUE (org_id, code)`. Owned by the Open Routing user/operator. Used as upsert key for Phase 5 bulk import, the cross-reference target for nested relationships, and the addressable identity in OpenAPI Import schemas. Future v0.2 DSL will reference catalog rows by `code` as well.
- **D04_1-02:** `code` is IMMUTABLE post-create in v0.1. PATCH requests containing a `code` field that differs from the persisted value return HTTP 422 with `ErrorCode=immutable_field` and `field=code` in the response body. Rename support deferred to v0.2 via a dedicated rename endpoint.
- **D04_1-03:** `code` format: lowercase strict regex `^[a-z][a-z0-9_]{0,63}$`. Letters, digits, underscores; must start with a letter; 1-64 chars. Lowercase chosen for shell/grep/DSL friendliness. Enforced at the handler layer (Layer 1, returns 400 `invalid_body`). NOT enforced via DB CHECK.
- **D04_1-04:** Examples of valid `code` values: `emp_001`, `skill_voice_tier1`, `queue_billing`, `channel_voice_primary`, `adapter_freeswitch_dc1`, `break_lunch`.
- **D04_1-05:** Empty `code` is invalid. NOT NULL + handler validation reject it.

**`external_id` Demotion (Area 2)**
- **D04_1-06:** `external_id` becomes `TEXT NULL` on all 6 entities. Partial unique index `(org_id, external_id) WHERE external_id IS NOT NULL`. Two rows in the same org can both have NULL external_id without colliding.
- **D04_1-07:** `external_id` is OPTIONAL on `Create*Request`, MUTABLE on `Update*Request`. Collision returns 409 `duplicate_external_id`.
- **D04_1-08:** OpenAPI `external_id` description tightened — quoted verbatim in `<specifics>` block.

**Migration Strategy (Area 3)**
- **D04_1-09:** Amend `000002_catalog_v0_1.up.sql` in place per D-61. No migration 003.
- **D04_1-10:** Backfill in the same migration via `UPDATE` statements BEFORE the NOT NULL is enforced. 4 entities derive `code` from `external_id` (lowercase + sanitize); adapters/break_reasons derive from `name` + UUID-suffix.

## Summary

Phase 04.1 corrects a contract-design defect identified by 4/4 cross-AI peer review consensus: `external_id` was conflated with user-facing identity. The fix introduces a universal `code` column across all 6 primary catalog entities (`agents`, `skills`, `queues`, `channels`, `adapters`, `break_reasons`), demotes `external_id` to optional integration mapping, drops the fragile `break_reasons.UNIQUE(org_id, name)`, and propagates the change through migration → OpenAPI → sqlc → handlers → tests in a single phase. The phase amends migration `000002_catalog_v0_1.up.sql` in place per D-61 (still editable until v0.1 ships).

The work is dominated by three categories of mechanical-but-precise edits: (1) PostgreSQL DDL changes spread across 6 table definitions in one migration file, with idempotent backfill UPDATE statements that must produce valid codes before the NOT NULL constraint flips; (2) ~41 OpenAPI yaml schema deltas across entity/ListItem/Create/Update/error-response components, all driving codegen-drift via `task gen`; (3) 6 handler files inheriting a shared `validateImmutableCode` helper for PATCH immutability and a constraint-name-introspect error mapper for the `duplicate_code` vs `duplicate_external_id` 409 distinction. Test deltas mirror the contract change: 5 new test scenarios × 6 entities = 30 test cases plus a fully regenerated two-org isolation fixture set.

**Primary recommendation:** Sequence the migration edit + backfill SQL + OpenAPI edits in Wave 1 (parallel-safe), then sqlc query updates + handler refactors in Wave 2, then per-entity test suites + isolation harness in Wave 3, then a Wave 4 cleanup that verifies `task gen` is clean and `task db:reset` rebuilds cleanly. The two architectural surprises captured here (oapi-codegen `pattern` is NOT auto-enforced by the strict-server runtime; OpenAPI has only ONE `*ListItem` schema currently — `AgentListItem`; the other 5 entities use the base entity schema for list items) shift the plan slightly from what CONTEXT.md anticipates.

### Pattern 1: PostgreSQL partial unique index for nullable external_id

**What:** Express "unique when present, multiple NULLs allowed" using `CREATE UNIQUE INDEX ... WHERE external_id IS NOT NULL`.

**When to use:** Every catalog entity whose `external_id` becomes nullable in 04.1. All 6 entities.

**Why this idiom (not `NULLS NOT DISTINCT`):** PostgreSQL's default treats each NULL as distinct from every other NULL — so a plain `UNIQUE (org_id, external_id)` would already allow multiple NULLs but would also fail when ALL non-NULL pairs collide [CITED: postgresql.org/docs/current/indexes-unique.html]. Phase 04.1's requirement matches the partial-index idiom exactly: "unique iff external_id IS NOT NULL". PG 15+ alternative `NULLS NOT DISTINCT` does the *opposite* (treats NULLs as equal) — wrong semantic for our case.

**Example DDL:**
```sql
-- Inside services/api/migrations/000002_catalog_v0_1.up.sql for each entity
CREATE TABLE agents (
    id            UUID PRIMARY KEY,
    org_id        UUID NOT NULL,
    code          TEXT NOT NULL,                      -- NEW
    external_id   TEXT NULL,                          -- WAS: TEXT NOT NULL
    name          TEXT NOT NULL,
    email         TEXT NOT NULL,
    enabled       BOOLEAN NOT NULL DEFAULT TRUE,
    version       INTEGER NOT NULL DEFAULT 1,
    created_at    TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at    TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    UNIQUE (org_id, code)                              -- NEW; gets auto-name `agents_org_id_code_key`
    -- DROPPED: UNIQUE (org_id, external_id)
);
CREATE UNIQUE INDEX ix_agents_org_external_id
    ON agents (org_id, external_id)
    WHERE external_id IS NOT NULL;                     -- NEW partial unique
-- Existing indexes preserved unchanged:
CREATE INDEX ix_agents_org_created ON agents (org_id, created_at DESC, id DESC);
CREATE INDEX ix_agents_org_name ON agents (org_id, lower(name) text_pattern_ops) WHERE enabled = TRUE;
```

The auto-generated constraint name for `UNIQUE (org_id, code)` is `agents_org_id_code_key` (Postgres default: `<table>_<col1>_<col2>_key`). This is what `pgErr.ConstraintName` returns and is the key by which D04_1-21 distinguishes the two 23505 flavors.

### Pattern 2: Handler-side regex validation (Layer 1 in this codebase)

**What:** Re-implement OpenAPI `pattern` enforcement at the handler boundary because oapi-codegen v2 doesn't generate it.

**When to use:** Every Create/Update handler for `code`. Reusable helper.

**Why this is needed (KEY FINDING):** oapi-codegen does NOT compile `pattern` schemas into Go regex validators in the strict-server flavor [CITED: github.com/oapi-codegen/oapi-codegen/discussions/1714]. The strict-server runtime decodes JSON, asserts required-field presence, and binds types — but `pattern`, `minimum`, `maximum`, `minLength`, `maxLength` are NOT enforced in the generated code. To get auto-validation you would wire `kin-openapi/openapi3filter.ValidateRequest` as middleware. **This project does NOT wire it** (verified by grep: zero `openapi3filter` references in `services/api/internal/`). 

This means D04_1-19's "Layer 1 = automatic via oapi-codegen" is INACCURATE FOR THIS CODEBASE. The handler IS the Layer 1 enforcer for `pattern`. The planner must include explicit `validateCodeFormat` calls in every Create handler (and in Update handlers when `req.Body.Code != nil`, BEFORE the immutability check, so a malformed PATCH gets 400 not 422).

**Example:**
```go
// services/api/internal/catalog/codecheck.go (NEW)
package catalog

import (
    "regexp"
)

// codeFormat is the canonical regex from D04_1-03. Compiled once at
// package init.
var codeFormat = regexp.MustCompile(`^[a-z][a-z0-9_]{0,63}$`)

// validateCodeFormat returns true if s matches D04_1-03 strict format.
// Handler maps false → 400 invalid_body with reason="invalid_code_format".
func validateCodeFormat(s string) bool {
    return codeFormat.MatchString(s)
}

// validateImmutableCode is the PATCH-only immutability check (D04_1-20).
// Returns true iff requested is empty (absent in PATCH body) or equals
// stored. False → handler maps to 422 immutable_field.
func validateImmutableCode(stored, requested string) bool {
    return requested == "" || requested == stored
}
```

### Pattern 3: Constraint-name introspection for distinct 409 mapping

**What:** When pgx returns a 23505 unique-violation, examine `pgErr.ConstraintName` to pick the right wire-shape `ErrorCode`.

**When to use:** Every Create and Update handler. Centralized in `catalog/errors.go`.

**Why:** Two distinct uniqueness constraints can fire on the same INSERT/UPDATE: the full `(org_id, code)` unique key OR the partial `(org_id, external_id)` unique index. The constraint-name suffix differs and is stable across migrations as long as you don't rename. Phase 04.1 picks deterministic names per Pattern 1 above. [CITED: github.com/jackc/pgx/wiki/Error-Handling]

**Example:**
```go
// services/api/internal/catalog/errors.go (EDIT — extend existing mapPgError)
package catalog

import (
    "errors"
    "net/http"
    "strings"

    "github.com/jackc/pgx/v5"
    "github.com/jackc/pgx/v5/pgconn"

    "github.com/luongdev/open-routing/services/api/internal/api"
)

// mapPgError translates a sqlc/pgx-returned error into the canonical
// (httpStatus, ErrorCode, reason) triple. The handler then wraps the
// triple in the operation-specific *JSONResponse type.
//
// 23505 unique-violations branch by constraint name:
//   - <tbl>_org_id_code_key            → 409 duplicate_code
//   - ix_<tbl>_org_external_id         → 409 duplicate_external_id
//   - any other 23505                   → 409 invalid_body (defensive — surfaces
//                                         schema drift rather than 500)
func mapPgError(err error, entity string) (int, api.ErrorCode, string) {
    if errors.Is(err, pgx.ErrNoRows) {
        return http.StatusNotFound, api.ErrorCodeNotFound, entity + "_not_found"
    }
    var pgErr *pgconn.PgError
    if errors.As(err, &pgErr) {
        switch pgErr.Code {
        case "23505":
            name := pgErr.ConstraintName
            switch {
            case strings.HasSuffix(name, "_org_id_code_key"):
                return http.StatusConflict, api.ErrorCodeDuplicateCode, "duplicate_code"
            case strings.HasPrefix(name, "ix_") && strings.HasSuffix(name, "_org_external_id"):
                return http.StatusConflict, api.ErrorCodeDuplicateExternalID, "duplicate_external_id"
            default:
                // Defensive: a future constraint we forgot to map → 409 with a
                // generic reason so clients still see "4xx, retry with new
                // values" rather than 5xx.
                return http.StatusConflict, api.ErrorCodeInvalidBody, "unique_violation:" + name
            }
        case "23503":
            return http.StatusUnprocessableEntity, api.ErrorCodeInvalidReference, "fk_violation"
        case "23514":
            return http.StatusUnprocessableEntity, api.ErrorCodeInvalidValue, "check_violation"
        }
    }
    return http.StatusInternalServerError, api.ErrorCodeInternal, "internal"
}
```

**Note for planner:** new `ErrorCode` enum values (`duplicate_code`, `duplicate_external_id`, `immutable_field`) must be added to `openapi/openapi.yaml` `components.schemas.ErrorCode` enum (D04_1-16) so `api.ErrorCodeDuplicateCode` etc. are emitted by codegen. CONTEXT.md's `<specifics>` block recommends names — use exactly those: `duplicate_code`, `duplicate_external_id` (already exists as `external_id_collision` reason but the ErrorCode value should be the new `duplicate_external_id`), `immutable_field`.

### Pattern 4: Idempotent migration backfill with collision dedup

**What:** Within the same migration body, after ALTER TABLE adds `code TEXT NULL`, run an UPDATE that derives a sanitized `code` from `external_id` (or `name`), then a second UPDATE that appends `_<n>` to collision rows via a window function, then ALTER TABLE ... SET NOT NULL.

**When to use:** Once, in `000002_catalog_v0_1.up.sql`, but the migration MUST be idempotent because D-61 keeps it editable and `task db:reset` re-runs from scratch.

**Why idempotent matters:** Plans Wave 1 includes a "run migration twice on identical seed data" smoke test (D04_1-11). If the backfill is wrapped in a CTE that uses `row_number() OVER (PARTITION BY org_id, code)`, running it twice on already-deduped data produces zero changes (no row will have row_number > 1).

**Concrete SQL pattern (per entity):**
```sql
-- agents — backfill code from external_id, sanitize per D04_1-03 regex constraints
-- Step 1: derive a candidate code; coerces non-letter prefixes to letter prefix (D04_1-03 says "must start with letter").
UPDATE agents
SET code = CASE
    WHEN substring(external_id from 1 for 1) ~ '^[a-zA-Z]$'
        THEN lower(regexp_replace(external_id, '[^a-zA-Z0-9_]', '_', 'g'))
    ELSE 'r_' || lower(regexp_replace(external_id, '[^a-zA-Z0-9_]', '_', 'g'))
END
WHERE code IS NULL;

-- Step 2: dedupe within (org_id, code) by appending _<n> to second+ occurrences.
-- This is a single self-contained UPDATE; rerunning it on already-deduped data
-- is a no-op (every partition has row_number=1 already).
WITH dups AS (
    SELECT id,
           row_number() OVER (PARTITION BY org_id, code ORDER BY created_at, id) AS rn
    FROM agents
)
UPDATE agents a
SET code = a.code || '_' || dups.rn::text
FROM dups
WHERE a.id = dups.id AND dups.rn > 1;

-- Step 3: enforce NOT NULL now that every row has a value.
ALTER TABLE agents ALTER COLUMN code SET NOT NULL;
ALTER TABLE agents ADD CONSTRAINT agents_org_id_code_key UNIQUE (org_id, code);
```

**Per-entity backfill source field:**
- agents, skills, queues, channels: `external_id` (the field already NOT NULL pre-04.1)
- adapters: `name` (no external_id existed) — plus optional UUID-suffix from `id` for collision safety: `lower(regexp_replace(name, '[^a-zA-Z0-9_]', '_', 'g')) || '_' || substring(replace(id::text, '-', ''), 1, 8)` is one approach per D04_1-10; but the row_number dedup step makes the UUID-suffix unnecessary if we just derive from name and let row_number resolve collisions. **Recommendation to planner: prefer the simpler "derive from name, let row_number dedup" because it's symmetric across all 6 entities and easier to read.** UUID-suffix is fragile (mixing different concerns) — use only if row_number proves insufficient at human review.
- break_reasons: `name` (no external_id existed) — same approach.

### Pattern 5: Postgres `regexp_replace` portability

**Confirmed:** `regexp_replace(input, '[^a-zA-Z0-9_]', '_', 'g')` is portable across PG14/15/16/17 [CITED: postgresql.org/docs/current/functions-string.html]. The `'g'` flag fires global replacement. The replacement string `'_'` is literal (no `\1` backreferences). `lower()` is a stdlib function unchanged across PG versions. Both functions handle NULL input by returning NULL — which is why Step 1 uses `WHERE code IS NULL` (skips rows that already have code, and the `CASE` expression on NULL `external_id` would itself return NULL safely).

**Edge case the planner must consider:** if `external_id` itself is NULL pre-04.1 (impossible per current schema, but hypothetically after a hypothetical earlier rollback), Step 1 leaves `code` NULL too, and Step 3's `ALTER TABLE ... SET NOT NULL` fails. Defensive: add a fallback `COALESCE(external_id, 'auto_' || substring(id::text, 1, 8))` inside the CASE. **Phase 04.1 reality check:** all 4 entities that had `external_id NOT NULL` pre-04.1 will produce a derived code; the CASE expression handles digit-prefix (adds `r_` prefix). For adapters/break_reasons deriving from name (always NOT NULL pre-04.1), this isn't an issue.

### Anti-Patterns to Avoid

- **DB CHECK constraint enforcing the `code` regex.** Rejected — D04_1-03 explicitly puts validation at the handler layer (matches agent_skills proficiency D-74 pattern). A DB CHECK would require regex_match function, which is overkill for v0.1; the handler is the single source of truth.
- **Trying to enforce immutability via DB trigger.** A trigger checking `OLD.code = NEW.code` would work but couples migration logic to handler error mapping. Trigger errors are 23P01 or similar and don't fit the existing `mapPgError` switch. Handler-side check stays consistent with D-74.
- **Combining `code` rename with Phase 04.1.** D04_1-DEFER-02 locks rename to v0.2 with a dedicated endpoint. Adding rename in Phase 04.1 would require cascade semantics across audit logs, import templates, and DSL refs — out of scope.
- **Adding migration 003 instead of editing 000002.** D-61 + D04_1-09 explicitly chose in-place edit. Migration 003 would leave the contradicted `external_id NOT NULL` constraint in the schema_migrations history; a fresh CI run via `task db:reset` would build the post-04.1 state but the migration history would suggest a two-step evolution that never actually happened in dev/test environments where `db:reset` runs.
- **Hand-rolling JSON marshaling for the new `code` field.** The codegen-drift gate ensures `task gen` produces the new `Code string` field; handlers consume it directly. Hand-edit of `types.gen.go` would be reverted by CI.
- **Using `pgerrcode.UniqueViolation` constant.** Adds a new dep; existing code uses string literal `"23505"` (catalog/errors.go:48). For consistency, Phase 04.1 should match the existing pattern. (Planner may revisit if a cross-cutting refactor introduces pgerrcode.)
- **Forgetting `task gen` after editing openapi.yaml.** The CI codegen-drift job will block the PR. The phase-final commit MUST include all 3 regenerated artifact paths: `services/api/internal/api/server.gen.go`, `services/api/internal/api/types.gen.go`, `web/packages/ui/src/api/generated.ts`.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Validating a regex pattern in Go | Custom string parser per character | `regexp.MustCompile(...).MatchString(s)` | Stdlib, correct, ~50ns/op for 64-char strings |
| Distinguishing 23505 constraints | Parse `pgErr.Detail` string with regex | `pgErr.ConstraintName` field | Detail string format is locale-dependent and not stable; ConstraintName is the documented stable accessor [CITED: github.com/jackc/pgx/wiki/Error-Handling] |
| Generating Go DTO types from OpenAPI | Hand-write struct mirroring spec | `task gen` (existing oapi-codegen pipeline) | CONTRACT-04 codegen-drift CI enforces this — hand-edits get reverted |
| Backfill collision resolution | Random suffix generator (`md5`, `gen_random_uuid`) | `row_number() OVER (PARTITION BY org_id, code)` window function | Deterministic, idempotent, makes the migration replay-safe; D04_1-11 |
| Wiring pattern validation across all handlers | Per-entity copy/paste of regex check | Shared `codecheck.go` helper (D04_1-20) | One helper, one test, six call sites; mirrors the proficiency validator pattern from Phase 3 P5 |
| Migration 003 to add new constraints | Two-step: 003 ADD code NULL → 004 SET NOT NULL | In-place edit of 000002 (D-61 + D04_1-09) | Pre-v0.1-ship, schema is malleable; fresh-db rebuild via `task db:reset` is canonical |
| Phase 5 import skipping new code field | Reuse existing `external_id`-based upsert | New `UpsertXByCode` query authored in 04.1, invoked in Phase 5 | Phase 04.1 ships the SQL primitive; Phase 5 wires it |

**Key insight:** Phase 04.1 is mostly schema/contract refactoring. The dangerous temptations are (a) trying to be cute with the migration to avoid the row_number step, (b) duplicating handler validation logic instead of using `codecheck.go`, and (c) introducing the new ErrorCode values directly in Go without going through openapi.yaml → codegen. All three are avoided by following the existing Phase 3 patterns.

## Common Pitfalls

### Pitfall 1: oapi-codegen `pattern` is NOT auto-enforced

**What goes wrong:** The planner / executor assumes putting `pattern: '^[a-z][a-z0-9_]{0,63}$'` in OpenAPI produces an auto-validating Go struct, so a malformed `code` returns 400 from the framework. It does NOT — the request reaches the handler unfiltered.

**Why it happens:** oapi-codegen v2 emits the pattern into the spec for documentation purposes but does not generate regex validators in `types.gen.go`. The validation lives in optional middleware (kin-openapi `openapi3filter.ValidateRequest`) that this codebase does NOT wire. Confirmed by grep: zero `openapi3filter` references in `services/api/internal/`. [CITED: github.com/oapi-codegen/oapi-codegen/discussions/1714, github.com/oapi-codegen/oapi-codegen/discussions/2053]

**How to avoid:** Implement Layer 1 validation in the handler EXPLICITLY via the shared `codecheck.go` helper. Every Create handler calls `validateCodeFormat(req.Body.Code)` BEFORE any DB call. Every Update handler that received a non-nil `Code` field calls the same check before the immutability check.

**Warning signs:** A test like `TestCreate_InvalidCodeFormat_Returns400` passes a body with `code: "UPPER"`, expects 400, but receives 500 (the INSERT succeeded with bad data) — that's the smoking gun for missing Layer 1.

### Pitfall 2: CONTEXT.md `<specifics>` points to wrong file path for error codes

**What goes wrong:** The `<specifics>` block in `04.1-CONTEXT.md` says "extend `services/api/internal/httputil/errors.go`". This file does NOT exist in the current codebase. The actual error map lives in `services/api/internal/catalog/errors.go` (the `mapPgError` function).

**Why it happens:** Documentation drift between CONTEXT and the post-Phase-3 layout. Phase 1's plans referenced a `httputil` package; it was reorganized into `middleware` and per-package locations during Phase 1/2 execution.

**How to avoid:** The new constants (`ErrorCodeDuplicateCode`, `ErrorCodeDuplicateExternalID`, `ErrorCodeImmutableField`) live in `services/api/internal/api/types.gen.go` (as members of the `ErrorCode` enum) once `openapi.yaml` is updated and `task gen` runs. The mapper logic in `catalog/errors.go` is what extends. No `httputil/errors.go` needs to be created.

**Warning signs:** A planner tries to create `internal/httputil/errors.go` from scratch — that's the leaky-abstraction bug.

### Pitfall 3: Existing `mapPgError` 409 mapping is BROKEN per SIMPLICITY-REVIEW

**What goes wrong:** Current `catalog/errors.go:48-49` maps every 23505 to `ErrorCode=version_conflict, reason="external_id_collision"`. This was flagged by the Phase 3 SIMPLICITY-REVIEW.md as MEDIUM severity ("pg error mapping hides entity-specific conflicts"). break_reasons uses `(org_id, name)` UNIQUE — `external_id_collision` is wrong there. Phase 04.1's new code adds two more constraints — without the constraint-name introspect (Pattern 3), all 23505s would still surface as the wrong wire shape.

**Why it happens:** The Phase 3 mapper was written when only one unique constraint per table existed (`(org_id, external_id)` on 4 entities + `(org_id, name)` on break_reasons). The shared mapper picked a single 23505 verdict. Phase 04.1 must fix this on the path to introducing TWO unique constraints per table.

**How to avoid:** Replace the existing `case "23505"` body with the constraint-name switch from Pattern 3. The fix is part of Phase 04.1 scope (CONTEXT.md `<specifics>` block implicitly accepts this by listing `errors.go` in the file map).

**Warning signs:** Any test expecting `ErrorCode=duplicate_code` receives `ErrorCode=version_conflict` — that's the existing-mapper-not-updated bug.

### Pitfall 4: Update*Request `Code` field — distinguishing absent vs present-but-empty vs equal-to-stored

**What goes wrong:** Strict-server unmarshals the PATCH body. The JSON field can be (a) absent — `code` key missing entirely, (b) present-with-empty-string — `{"code": ""}`, (c) present-with-stored-value — `{"code": "emp_001"}`, (d) present-with-different — `{"code": "emp_002"}`. Different semantics:
- (a) absent → no change intended → succeed
- (b) empty → MALFORMED (D04_1-05 says empty is invalid) → 400 invalid_body
- (c) same → no change → succeed
- (d) different → 422 immutable_field

**Why it happens:** oapi-codegen with `nullable: false` + non-required emits the field as `*string`. `nil` distinguishes "absent" from "present with empty/zero value". But `json.Unmarshal` of `{"code": ""}` gives `*string` pointing to `""` (NOT nil). The handler MUST check both nil-ness AND empty-ness.

**How to avoid:** The `Update*Request` schemas should declare `code` as `type: string, pattern: '^[a-z][a-z0-9_]{0,63}$'`, NOT `nullable: true`. Then oapi-codegen emits `Code *string` (because the field is not required) and the handler logic is:
```go
if req.Body.Code != nil {
    if !validateCodeFormat(*req.Body.Code) {
        return 400 invalid_body / "invalid_code_format"
    }
    if !validateImmutableCode(stored.Code, *req.Body.Code) {
        return 422 immutable_field / "code"
    }
}
// proceed with update — code is unchanged or matches stored
```

This handles all four cases correctly. JSON `null` for code is treated by oapi-codegen as the field's zero value (different from `*string` semantics in some versions) — recommend the planner verify by adding a test `TestUpdate_CodeAsJsonNull_Returns400_InvalidBody` to lock the behavior.

### Pitfall 5: Migration backfill collision with existing `task db:reset` workflow

**What goes wrong:** D-61 keeps migration 000002 editable. `task db:reset` drops the DB, recreates it, and re-applies all migrations from scratch — so after Phase 04.1's edits, every developer running `task db:reset` will hit the new schema on the next run. BUT: a developer with an already-applied 000002 (from before the edit) who pulls Phase 04.1 changes and runs `migrate up` will see "no change" — golang-migrate compares versions, not content [CITED: golang-migrate dirty-secret post @ atlasgo.io].

**Why it happens:** `schema_migrations` table tracks `(version, dirty)`. Editing the migration file does NOT re-apply the file. Only `task db:reset` (or explicit `migrate down; migrate up`) sees the new content.

**How to avoid:** Phase 04.1's first plan step MUST include a clear directive: "After editing 000002, you MUST run `task db:reset` before testing. `migrate up` is a no-op." Add this to the plan's preconditions section. The CI runs `task db:reset` (via testcontainer fresh-DB bring-up) so CI catches the schema, but local dev with a stale DB would silently use the old schema.

**Warning signs:** Tests run locally with the new code, fail with `column "code" does not exist`, but pass in CI. That's the stale-local-DB bug.

### Pitfall 6: `AgentListItem` is the ONLY ListItem schema; other 5 entities reuse base schema

**What goes wrong:** CONTEXT.md `<specifics>` block says "6 `*ListItem` schemas gain `code`". Reality: only `AgentListItem` is a separate schema. Skills, Queues, Channels, Adapters, BreakReasons list responses use `items: { $ref: "#/components/schemas/Skill" }` (the full entity schema, not a list-item subset). The plan estimate of "~28 schema edits + ~12 error-response edits + 1 info-block edit = ~41" overestimates ListItem-specific edits.

**Why it happens:** The list-item-with-skills-stripped pattern was implemented only for agents (OQ-1A — agents have a `skills` embedded array on detail responses but flat list items). Other entities have no embedded sub-resource and reuse the base schema.

**How to avoid:** Plan to:
- Add `code` to 6 entity schemas (Agent, Skill, Queue, Channel, Adapter, BreakReason)
- Add `code` to ONE list-item schema (AgentListItem)
- Add `code` to 6 Create*Request schemas
- Add `code` (immutable-acknowledged) to 6 Update*Request schemas
- Update 6 path-level 409 response descriptions and add 422 immutable_field responses
- Add 3 new `ErrorCode` enum values
- Update 1 `info.description` block

True edit count: **~25 entity/request schema edits + ~12 error-response edits + 3 ErrorCode additions + 1 info-block edit ≈ ~41 deltas** (the count matches CONTEXT but the distribution differs from what `<specifics>` describes). The planner should verify by reading openapi.yaml lines 336 (AgentListItem) and grep for `ListItem` — confirms only 1 such schema.

### Pitfall 7: `CreateAdapter` has NO 409 response currently

**What goes wrong:** CONTEXT.md says all 6 entities get the new 409 `duplicate_code` and `duplicate_external_id` wire shapes. But `CreateAdapter` (openapi.yaml ~lines 2440-2470) has no `"409":` block today — adapters had no unique constraint beyond PRIMARY KEY(id), so 23505 was impossible.

**Why it happens:** Phase 3 D04_1-06 adds `(org_id, code)` UNIQUE (and partial unique on external_id) to adapters. 23505 becomes possible. The spec MUST add a 409 response shape for CreateAdapter and UpdateAdapter.

**How to avoid:** When the planner enumerates path edits, include for adapters:
- New `"409":` block on CreateAdapter (mirror CreateAgent's 409 structure but FLAT ErrorResponse, not oneOf — matches Skill/Queue/Channel pattern)
- New `"422":` block on UpdateAdapter for the immutable_field response
- Add 422 response on CreateAdapter? — no, format failures are 400 (Layer 1). 422 immutable_field is PATCH-only. UpdateAdapter gets 422.

**Warning signs:** Adapter integration test fails on a duplicate `code` insert because the strict-server has no `CreateAdapter409JSONResponse` type to wrap the error in — the handler can't return what doesn't exist.

### Pitfall 8: Test fixtures' `code` values must respect the regex

**What goes wrong:** Existing `services/api/test/isolation/catalog_test.go` uses bodies like `{"external_id": "ext-iso-a", "name": "Alice", "email": "..."}`. The simple rename `"external_id"→"code"` would produce `code: "ext-iso-a"` — which starts with a letter but contains a hyphen → fails D04_1-03 regex.

**Why it happens:** Phase 3 used hyphen-separated external_id values for human readability. The Phase 04.1 regex disallows hyphens. Mechanical search-replace breaks the tests.

**How to avoid:** Test fixtures need editorial fixup, not just rename. Replace `ext-iso-a` → `iso_emp_a` (underscores only). The Phase 04.1 plan must include a step "audit test bodies for code-regex compliance" with concrete fixture-value examples per D04_1-22.

**Warning signs:** All integration tests fail with `400 invalid_code_format` — the Layer 1 check is working but the fixtures are stale.

### Pitfall 9: `code`-search index NOT needed; primary UNIQUE covers it

**What goes wrong:** A planner might add `CREATE INDEX ix_<entity>_org_code ON <entity> (org_id, code)` thinking it improves Phase 5 import lookup performance.

**Why it happens:** Phase 5 uses `ON CONFLICT (org_id, code) DO UPDATE` (D04_1-18 UpsertXByCode). The `UNIQUE (org_id, code)` constraint that Phase 04.1 adds AUTOMATICALLY creates a unique B-tree index named `<table>_org_id_code_key`. Postgres uses this index for both the uniqueness check AND for point lookups [CITED: postgresql.org/docs/current/indexes-unique.html]. Adding a separate `ix_*_org_code` would be redundant and double the index maintenance cost.

**How to avoid:** Plan should explicitly note: NO new explicit index on `(org_id, code)` is needed. The UNIQUE constraint provides it. Same applies to the partial unique index on external_id — it serves both uniqueness and point lookup.

### Pitfall 10: oneOf 409 wire shape for CreateAgent vs FLAT for others

**What goes wrong:** From Phase 3 (Pitfall 2 in 03-PATTERNS.md): `CreateAgent409` is a `oneOf` union (`ErrorResponse | VersionConflictErrorResponse`), but `CreateSkill409`, `CreateQueue409`, `CreateChannel409`, `CreateBreakReason409` are FLAT `ErrorResponse`. The 04.1 handler refactor must preserve this asymmetry.

**Why it happens:** CreateAgent's 409 has historical reasons (it handled both external_id collision AND skills-related version conflicts) so the spec used oneOf. Other CREATEs only had one 23505 source.

**How to avoid:** When updating the 6 handler 409 paths to surface `duplicate_code` vs `duplicate_external_id`:
- `CreateAgent`: continue using `body := api.CreateAgent409JSONResponseBody{}; _ = body.FromErrorResponse(api.ErrorResponse{...})` — the union helper
- `CreateSkill/Queue/Channel/BreakReason`: continue using `api.CreateSkill409JSONResponse(api.ErrorResponse{...})` — flat
- `CreateAdapter` (NEW 409): use the flat pattern (matches the 4 simpler entities)

Each call site is mechanically identical except for the wrapper type. The shared `mapPgError` returns the triple `(httpStatus, ErrorCode, reason)`; the handler chooses the wrapper.

### Pitfall 11: Down migration symmetry for the partial unique index

**What goes wrong:** The down migration drops tables (existing behavior). Phase 04.1's down should also be aware that any row inserted post-04.1 with NULL external_id cannot exist if the down restores `external_id NOT NULL`. Since down migrations in v0.1 are documentation-only (D04_1-12), the issue is theoretical, but a planner who tries to run a down-up cycle in CI would hit `NOT NULL constraint failed` on the rerun.

**Why it happens:** Existing down migration drops tables wholesale and recreates _scaffold. A future planner might rewrite to be column-additive — that's where the trap lives.

**How to avoid:** Keep the down migration as drop-tables + recreate-scaffold (existing pattern). Document in the migration comment: "Down migration is for completeness; v0.1 uses task db:reset for testing."

## Open Questions

1. **Should `Update*Request.code` be optional (`*string`) or required-with-default-stored?**
   - What we know: D04_1-15 says "code is immutable — passing a different value returns HTTP 422". The simpler implementation makes code optional in Update*Request and tolerates absence (don't validate, don't compare).
   - What's unclear: Whether the OpenAPI examples should show `code` in Update payloads to communicate intent, or omit it to discourage clients from sending it.
   - Recommendation: Make `code` optional in `Update*Request` schemas (no `required: [code]` entry). Document in the schema description that "if `code` is sent, it MUST equal the stored value; mismatched values return 422". Most admin UI clients will send the full body from the last GET, so they'll naturally include `code` — and the immutable check is a safety net. **Planner: this matches the existing `version` field's PATCH idiom (required-on-update) but code is voluntary; lock in the plan.**

2. **Backfill source for `adapters` and `break_reasons` — `name` alone, or `name + UUID-suffix`?**
   - What we know: D04_1-10 says adapters/break_reasons backfill is `lower(regexp_replace(name, ...)) || '_' || substring(replace(id::text, '-', ''), 1, 8)`. The UUID suffix guarantees uniqueness even if two rows have the same name.
   - What's unclear: Whether the row_number() dedup step makes the UUID-suffix redundant.
   - Recommendation: Use `lower(regexp_replace(name, '[^a-zA-Z0-9_]', '_', 'g'))` alone for the first UPDATE, then let the row_number dedup step (Pattern 4 Step 2) resolve any collisions. The UUID-suffix bakes implementation noise into the user-facing code (a code like `freeswitch_a1b2c3d4` is ugly compared to `freeswitch_2`). **Planner: prefer simplicity unless the executor finds row_number is insufficient.**

3. **Should `validateCodeFormat` reject leading/trailing whitespace before regex check, or rely on the regex?**
   - What we know: The regex `^[a-z][a-z0-9_]{0,63}$` is anchored at both ends — whitespace would fail it.
   - What's unclear: Whether the handler should TRIM the incoming string (common ergonomics) or fail outright.
   - Recommendation: Fail outright. D04_1-CONTEXT Deferred Ideas item explicitly rejects "request-time auto-lowercasing" for the same reason — strict validation gives clear feedback. Whitespace silently trimmed would mask client bugs. Plan a single test `TestCreate_CodeWithLeadingSpace_Returns400` to lock the behavior.
