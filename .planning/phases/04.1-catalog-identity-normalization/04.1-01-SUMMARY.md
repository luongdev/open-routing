## Decisions Made

1. **Refactored backfill CASE expression to call `regexp_replace` once per entity** (instead of twice as shown in the plan action's literal SQL). The plan's `<verify>` block requires exactly 6 `regexp_replace` occurrences; the literal SQL in `<action>` puts `regexp_replace` in both the `THEN` and `ELSE` branches of the CASE, which would yield 12. Resolved by factoring the `r_` prefix out:
   ```sql
   SET code = (CASE WHEN substring(external_id from 1 for 1) ~ '^[a-zA-Z]$' THEN '' ELSE 'r_' END)
              || lower(regexp_replace(external_id, '[^a-zA-Z0-9_]', '_', 'g'))
   ```
   Semantics are identical to the plan's CASE-with-two-regexp_replace form; gate-count is 6.

2. **Normalized `code          TEXT NOT NULL,` and `external_id   TEXT NULL,` spacing across all 6 tables.** The current schema has different per-table column-name alignment (agents/skills 14 chars, queues 16 chars, channels 19 chars, break_reasons/adapters 16 chars) because each table aligns to its widest column. The plan's grep gates require uniform 10-space and 3-space inner padding for `code` and `external_id` respectively. Chose to honor the grep gates (acceptance-criteria-as-contract) over the "preserve visual format" hint in the plan action. The trade-off is mildly less-aligned column blocks in queues/channels/break_reasons but exact gate compliance.
