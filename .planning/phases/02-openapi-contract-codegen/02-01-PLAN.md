<objective>
Produce four ASCII paper-sketches of high-complexity admin screens BEFORE the OpenAPI spec is authored, so any awkward response shape (e.g. flat skills array on agent detail, error envelope mismatch on bulk import) is caught and resolved before the spec is locked.

Purpose: D-33 + D-34 mandate sketch-first validation. The four screens chosen each cover a specific API-shape risk:
  1. Agent detail/edit — validates N:M agent_skills embedding choice
  2. Bulk import result — validates HTTP 207 BulkImportResult schema
  3. Agent status panel — validates STATE-02..STATE-07 transition request body, engaged_channel, wrapup_until display, post_interaction_state semantics
  4. Catalog list (generic) — validates cursor pagination, include_disabled, name search

Output: A single committed markdown file `02-UI-SKETCHES.md` containing all four sketches plus an OPEN QUESTIONS section per sketch flagging any spec adjustments needed.
</objective>

Create `.planning/phases/02-openapi-contract-codegen/02-UI-SKETCHES.md` with this structure (per D-33):

1. Top-of-file header:
   - Title: `# Phase 2: UI Sketches — API Shape Validation`
   - Status block: `**Purpose:** Contract validation only. Per D-33/D-34, these sketches exist so awkward API shapes get caught before openapi.yaml is locked. They are NOT UI implementation — Phase 6 owns real UI.`
   - ASCII convention note: `**ASCII convention:** Box-drawing characters (┌─┐│└┘├┤┬┴┼) for frames; brackets [Button] for buttons; (•) for radio; [x]/[ ] for checkboxes; --- for separators. Each sketch is 30-50 lines per D-33.`

2. Four `## Sketch N: <name>` sections in this order:

   **Sketch 1: Agent detail/edit** — validates N:M agent_skills shape (per D-33 item 1; covers CAT-01, CAT-03)
   - Show the screen rendering an agent with embedded skills array (NOT a separate GET /agents/{id}/skills call). Each skill row shows skill name + proficiency (1-10) + a remove button.
   - Include states: loading (skeleton), error (using canonical envelope `{error, reason, request_id}`), empty (no skills assigned), populated.
   - Show the "Add skill" affordance — dropdown listing org's skills (paginated cursor-based per CAT-10), plus proficiency input with `min=1 max=10` validation.
   - Show the `version` field hidden in form state so an update sends it for CAT-08 optimistic concurrency; show the 409 reload-prompt affordance: "Changed by someone else, reload?".
   - End with `### OPEN QUESTIONS` listing at least: "Embed skills array on Agent or use separate /agents/{id}/skills endpoint?" (decide based on whether list-view also needs skills); "Does `proficiency` validation happen client-side, server-side, or both?".

   **Sketch 2: Bulk import result** — validates 207 multi-status shape (per D-33 item 2; covers IMP-04, IMP-05, IMP-08)
   - Show post-upload result screen with: top-line counts (total: N, succeeded: M, failed: K), succeeded ids list (collapsible), failed-rows table (columns: row, field, error code, reason — matches D-37 BulkImportResult schema).
   - Show pre-upload state: file picker, entity-type dropdown (6 entities), schema_version=v0.1 hidden field, 50MB/500-row caps shown as helper text per IMP-07.
   - Show error states: 413 (too large) routing to "use async v0.2 path" message; 400 (schema_version mismatch) listing supported versions.
   - End with `### OPEN QUESTIONS` listing at least: "Should the failed[] rows array include the original row content for re-edit, or just the (row, field, error, reason) tuple?"; "Is the schema_version a query param or a header?".

   **Sketch 3: Agent status panel** — validates state transitions (per D-33 item 3; covers STATE-01..STATE-07)
   - Show current status display (one of: Ready, NotReady, Break, Engaged, WrapUp, Offline) with `state_version` visible (for STATE-08 monotonic check).
   - Show allowed-transition buttons rendered conditionally based on current status (e.g., Ready → [Go on Break ▾] [Set to NotReady]; Break → [Back to Ready] [NotReady]; Engaged → [Set post-interaction: Ready / NotReady]).
   - For the Ready → Break button: dropdown of break_reasons filtered by org (CAT-07); each reason carries a `routable` flag indicator (STATE-10's IsRoutable).
   - For Engaged: show engaged_channel value (voice | chat | email per STATE-05); show wrapup_until countdown if status==WrapUp (STATE-07 — server-owned TTL).
   - Show invalid-transition error rendering: HTTP 409 with body `{error: "invalid_transition", reason, request_id, from, to}` per D-37.
   - End with `### OPEN QUESTIONS` listing at least: "Does PATCH /agents/{id}/status accept a single transition or batched transitions?"; "How is the engaged_channel parameter shaped on system-initiated Ready → Engaged transitions?".

   **Sketch 4: Catalog list (generic)** — validates pagination + filtering (per D-33 item 4; covers CAT-09, CAT-10)
   - Use 'agents' as the canonical example. Show: list table with columns (id, external_id, name, email, enabled, version, created_at), name search box (case-insensitive per CAT-10), include_disabled toggle (CAT-09), Next-page button with opaque cursor.
   - Show response envelope: `{ items: [...], next_cursor: "...", has_more: true }` (planner picks shape; spec will lock this).
   - Show empty state (no rows), error state (using canonical envelope), and loading state.
   - End with `### OPEN QUESTIONS` listing at least: "Is the cursor opaque base64 or a structured `?after=<created_at>,<id>` pair?"; "Is `name` search prefix-only or substring (CAT-10 says case-insensitive but does not say substring vs prefix)?".

3. Final section `## Spec Author Checklist` listing the cross-sketch invariants the spec author MUST encode in `openapi.yaml`:
   - Canonical error envelope schema `ErrorResponse { error, reason, request_id }` per D-35
   - Closed enum `ErrorCode` with exactly the 10 codes from D-36
   - Special-case response shapes (D-37): CAT-08 with `current: <EntitySchema>`, STATE-03 with `from`/`to`, IMP-05 with `BulkImportResult`
   - Pagination response envelope reused across all 6 list endpoints
   - `proficiency` integer with `minimum: 1` / `maximum: 10` validation

Total length target: 150-220 lines (4 sketches × ~40 lines + header + checklist). Use code fences ```` ``` ```` to wrap ASCII art so markdown renderers preserve spacing.

DO NOT design the actual UI components, color tokens, or interactions. The sketches exist to make API shape decisions visible, not to specify UI. Where two API shape options seem equally valid, list both in the sketch's OPEN QUESTIONS — the spec author resolves them in Plan 02.
